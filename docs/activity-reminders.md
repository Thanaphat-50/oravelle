# แจ้งเตือนกิจกรรมล่วงหน้า

ผู้ใช้เลือกได้ว่าจะให้เตือนกิจกรรมเมื่อไร: **ไม่เตือน** (ค่าเริ่มต้น) / **ตรงเวลา** / **ก่อน 15 นาที** / **ก่อน 30 นาที** / **ก่อน 1 วัน**
ใช้ได้กับกิจกรรมครั้งเดียวที่มีวันและเวลาแน่นอนเท่านั้น

## ใครตั้งเตือนได้

| ใคร | ตั้งจากที่ไหน |
|---|---|
| ผู้สร้างกิจกรรม | ฟอร์มเพิ่ม/แก้ไขกิจกรรม หรือหน้ารายละเอียดกิจกรรม |
| สมาชิกในกลุ่ม (กิจกรรมที่แชร์ในกลุ่ม) | หน้ารายละเอียดกิจกรรม (กดที่รายการ) ไม่ต้องมีสิทธิ์แก้ไข |
| กิจกรรมส่วนตัว | เจ้าของเท่านั้น |

- แต่ละคนมีการเตือนของตัวเอง (1 คน 1 ค่าต่อกิจกรรม) และไม่เห็นค่าของคนอื่น
- เซิร์ฟเวอร์ตรวจสิทธิ์ 2 ครั้ง: ตอนตั้งเตือน และตอนจะส่งจริง
- การเตือนที่ยังไม่ส่งถูกยกเลิกเมื่อ: ออกจากกลุ่ม / ถูกนำออกจากกลุ่ม / ลบกลุ่ม / กิจกรรมถูกเปลี่ยนเป็นส่วนตัว (เฉพาะของสมาชิกคนอื่น) / กิจกรรมถูกลบ

## เวลาและเขตเวลา

กิจกรรมที่สร้างหรือแก้ไขจากแอปเวอร์ชันใหม่เก็บ:

- `starts_at` = ช่วงเวลาจริงแบบ UTC (แอปต้องส่งพร้อมเขตเวลา เช่น `2026-11-20T03:00:00Z` ถ้าไม่มีเขตเวลา เซิร์ฟเวอร์ไม่รับ)
- `timezone` = เขตเวลา IANA ของเครื่องผู้สร้าง เช่น `Asia/Bangkok`
- `activity_date` = เวลาตามนาฬิกาในเขตเวลานั้น (เก็บต่อไว้ให้แอปเวอร์ชันเก่าและตัวกรอง "วันนี้/เกินกำหนด")

สมาชิกที่อยู่ต่างเขตเวลาเห็นเวลาตามนาฬิกาเครื่องตัวเอง เพราะแอปแปลง `starts_at` เป็นเวลาท้องถิ่น
หน้ารายละเอียดยังแสดงเวลาที่ผู้สร้างตั้งไว้ พร้อมชื่อเขตเวลา ถ้าต่างจากเครื่องของผู้ดู

เวลาเตือน = `starts_at` − จำนวนนาทีที่เลือก
"ก่อน 1 วัน" คือ 24 ชั่วโมงจริง: ถ้าช่วงนั้นมีการเปลี่ยนเวลาฤดูร้อน (DST) นาฬิกาตอนเตือนอาจต่างจากเวลาเริ่มกิจกรรม 1 ชั่วโมง

## ข้อมูลเก่า (กิจกรรมก่อนมีระบบเตือน)

- กิจกรรมเดิมมีแค่ `activity_date` ซึ่งเป็นนาฬิกาเครื่องผู้ใช้ ไม่รู้ว่าเป็นเขตเวลาไหน
- migration **ไม่แปลงข้อมูลเดิม** ไม่เดาว่าเป็นเวลาไทย: `starts_at` ของกิจกรรมเดิมจึงเป็น NULL และเวลาที่แสดงไม่เลื่อน
- กิจกรรมเดิมที่มีวันเวลาจะมีค่า `needs_time_confirmation = true` ซึ่งยังตั้งเตือนไม่ได้
  - เจ้าของเปิด "แก้ไข" ตรวจวันเวลาแล้วกดบันทึก (ใช้เขตเวลาของเครื่องนั้น) จากนั้นจึงตั้งเตือนได้
  - สมาชิกคนอื่นเห็นข้อความว่าต้องรอผู้สร้างยืนยันเวลา

## แอปเวอร์ชันเก่า

- แอปเก่าส่งแค่ `activity_date` ไม่มีเขตเวลา และไม่มีหน้าตั้งเตือน
  - สร้างกิจกรรมจากแอปเก่า: `starts_at` = NULL จึงตั้งเตือนไม่ได้ จนกว่าเจ้าของจะยืนยันเวลาในแอปใหม่
  - แก้ไขจากแอปเก่าโดยส่งวันเวลาเดิมกลับมา (เช่น แก้แค่ชื่อ): ช่วงเวลาจริงและการเตือนยังอยู่เหมือนเดิม
  - แก้ไขจากแอปเก่าแล้วเปลี่ยนวันเวลา: เซิร์ฟเวอร์ไม่รู้เขตเวลา จึงพักการเตือน (`paused`) รอเจ้าของยืนยันเวลาในแอปใหม่
- รายการกิจกรรมยังส่ง `activity_date` รูปแบบเดิม แอปเก่าแสดงผลเหมือนเดิม
- แอปเก่าเปิดการแจ้งเตือนประเภท `activity_reminder` ไม่ได้ แต่ยังเห็นข้อความในหน้าแจ้งเตือน

## เปลี่ยนแปลงหลังตั้งเตือน

| เหตุการณ์ | ผล |
|---|---|
| เปลี่ยนวันเวลา | คำนวณเวลาเตือนของทุกคนใหม่ ถ้ายังอยู่ในอนาคตจะรอส่ง ถ้าผ่านไปแล้วจะไม่ส่ง (`expired`) |
| เปลี่ยน/ปิดการเตือนของตัวเอง | กำหนดเดิมถูกยกเลิก (เลข `version` เพิ่ม ทำให้งานส่งที่ค้างของกำหนดเก่าไม่ส่ง) |
| ทำเสร็จ | พักการเตือนที่ยังไม่ส่ง (`paused`) |
| กลับเป็นยังไม่เสร็จ | ตั้งใหม่เฉพาะการเตือนที่ยังอยู่ในอนาคต การเตือนที่ส่งไปแล้วไม่ส่งซ้ำ |
| ลบกิจกรรม | ลบการเตือนทั้งหมด |
| ล้างวันเวลา | พักการเตือน |

ถ้าเวลาเตือนที่เลือกผ่านไปแล้ว แอปจะให้เลือกใหม่ และเซิร์ฟเวอร์ตอบ 422 (`code: reminder_past`) ไม่บันทึกแบบเงียบ ๆ

## การส่ง

คำสั่ง `php artisan activities:send-reminders` (ตั้งเวลาไว้ใน `routes/console.php`)

1. หาการเตือนที่ถึงเวลา (`pending` และ `remind_at <= ตอนนี้`)
2. ล็อกแถวทีละรายการ แล้วตรวจซ้ำ: สถานะ / `version` / กิจกรรมยังอยู่ / ยังไม่เสร็จ / เวลายังตรง / ผู้ใช้ยังมีสิทธิ์เห็น
3. สร้างรายการแจ้งเตือนในแอป 1 รายการต่อคนต่อกำหนด แล้วส่ง push ไปทุกเครื่องของบัญชีนั้น
   - Token ที่ใช้ไม่ได้แล้วถูกลบ (ระบบ push เดิม)

เรื่องความถูกต้องของการส่ง:

- รันซ้อนกันหรือหลาย worker ก็ส่งครั้งเดียว: ล็อกแถว + เปลี่ยนสถานะใน transaction เดียวกับการสร้างรายการแจ้งเตือน
- ล้มกลางทาง: transaction ย้อนกลับ การเตือนยังเป็น `pending` และรอบถัดไปลองใหม่
- ระยะผ่อนผัน (`grace_minutes`): ถ้าช้ากว่ากำหนดเกินค่านี้ (เช่น Scheduler หยุดไปนาน) จะไม่ส่ง (`expired`) เพื่อไม่ให้การเตือนเก่าเด้งพร้อมกันจำนวนมาก
- ข้อความไม่มีชื่อหรือรายละเอียดกิจกรรม (แสดงบนหน้าจอล็อกได้) เช่น "กิจกรรมของคุณจะเริ่มในอีก 15 นาที · แตะเพื่อดูรายละเอียด"
- กดแจ้งเตือนแล้วเปิดหน้ารายละเอียดกิจกรรม ทั้งตอนเปิดแอปอยู่และตอนแอปปิด
  - ถ้าต้องเข้าสู่ระบบก่อน จะเปิดให้หลังเข้าสู่ระบบ (ใช้กลไกเดิมของแอป ยังไม่ได้ทดสอบกับ push จริงบนมือถือ)
  - กิจกรรมถูกลบหรือไม่มีสิทธิ์แล้ว: แสดงข้อความแจ้ง ไม่แสดงข้อมูลเดิม
- **ไม่รับประกันว่าตรงนาทีเป๊ะ**: ช้าได้สูงสุดประมาณ 1 รอบของ Scheduler บวกเวลาส่งของ Firebase

## ค่าที่ตั้งได้ (`config/reminders.php`)

| Environment variable | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `ACTIVITY_REMINDER_EVERY_MINUTES` | 5 | รันคำสั่งส่งทุกกี่นาที |
| (คำนวณให้) `grace_minutes` | ค่าที่มากกว่าระหว่าง 15 กับ 2 × รอบ | ช้าได้ไม่เกินกี่นาทีจึงยังส่ง |

## Laravel Cloud: สิ่งที่ต้องตั้งค่า

1. **Scheduler ต้องเปิด** (เปิดไว้แล้วสำหรับงานคำสั่งซื้อ) ไม่มีอะไรต้องเพิ่ม
   - งานคำสั่งซื้อ `orders:expire` ยังรันทุกชั่วโมงเหมือนเดิม
   - งานเตือนกิจกรรมแยกเป็นอีกงาน ใช้ `withoutOverlapping` และ `onOneServer` (ใช้ lock จาก cache แบบ database ที่มีอยู่)
2. **ไม่ต้องมี Queue worker**: ส่งในคำสั่งเลย ส่วน push ทำหลังคำสั่งจบ (ใช้กลไก defer เดิม)
3. migration ใหม่ (`2026_11_20_100000_add_reminders_to_activities`) รันอัตโนมัติตอน deploy
   - เพิ่มคอลัมน์และตารางใหม่เท่านั้น ไม่แก้ข้อมูลเดิม และรันซ้ำได้
4. (ไม่บังคับ) ตั้ง `ACTIVITY_REMINDER_EVERY_MINUTES` ถ้าต้องการเปลี่ยนรอบ แล้ว deploy ใหม่

### ค่าใช้จ่าย (Scale to zero)

App cluster เปิด Scale to zero ไว้ (หลับเมื่อไม่มีคำขอ 5 นาที) และ Scheduler ปลุกแอปทุกครั้งที่มีงาน

| รอบ | ความแม่นยำ | ค่าเครื่อง |
|---|---|---|
| 5 นาที (ค่าเริ่มต้น) | ช้าไม่เกิน ~5 นาที | แอปแทบไม่ได้หลับ ค่าเครื่องเกือบเท่าเปิดตลอดเดือน |
| 15 นาที | ช้าได้ถึง ~15 นาที ("ก่อน 15 นาที" อาจมาถึงตอนกิจกรรมเริ่ม) | หลับได้บางช่วง |
| 30 นาที | ช้าได้ถึง ~30 นาที ไม่เหมาะกับ "ตรงเวลา/ก่อน 15 นาที" | ประหยัดกว่า |

ตรวจค่าใช้จ่ายจริงในหน้า Usage ของ Laravel Cloud หลังเปิดใช้ แล้วค่อยปรับรอบ ไม่ต้องเปิดบริการเสียเงินเพิ่ม

## API

| Method | Path | ใช้ทำอะไร |
|---|---|---|
| POST | `/api/activities` | สร้างกิจกรรม: `starts_at` + `timezone` + `reminder_offset` (ไม่บังคับ) |
| PATCH | `/api/activities/{id}` | แก้ไขกิจกรรม (เจ้าของ): ส่ง `reminder_offset` เมื่อเปลี่ยนการเตือน |
| GET | `/api/activities/{id}` | รายละเอียดกิจกรรม: 404 ถ้าถูกลบหรือไม่มีสิทธิ์ |
| PUT | `/api/activities/{id}/reminder` | ตั้งเตือนของตัวเอง: `{offset: null\|0\|15\|30\|1440}` |

ข้อมูลกิจกรรมมี `starts_at`, `timezone`, `my_reminder` (offset / label / remind_at / status), `can_remind`, `needs_time_confirmation`

รหัสข้อผิดพลาด (422):

| code | ความหมาย |
|---|---|
| `no_time` | กิจกรรมยังไม่มีวันเวลา |
| `time_unconfirmed` | กิจกรรมเดิมที่ต้องยืนยันวันเวลาก่อน |
| `completed` | กิจกรรมทำเสร็จแล้ว |
| `reminder_past` | เวลาเตือนที่เลือกผ่านไปแล้ว |

## ข้อจำกัด

- ตัวกรอง "วันนี้/เกินกำหนด" ยังใช้นาฬิกาของผู้สร้าง (`activity_date`) เทียบกับนาฬิกาเครื่องผู้ดู
  - สมาชิกต่างเขตเวลาอาจเห็นกิจกรรมอยู่ในวันที่ต่างจากเวลาที่แสดง 1 วันได้
- ยังไม่มีกิจกรรมแบบทำซ้ำ (ใช้ได้กับกิจกรรมครั้งเดียว)
- ถ้าผู้ใช้ปิดการแจ้งเตือนของเครื่อง การเตือนจะอยู่ในหน้าแจ้งเตือนของแอปเท่านั้น
  - หน้ารายละเอียดแสดงสถานะนี้ และมีปุ่มไปหน้าตั้งค่า
- เครื่องที่อ่านชื่อเขตเวลาไม่ได้: แอปใช้ส่วนต่างเวลาเต็มชั่วโมงแทน (เช่น `Etc/GMT-7`)
  - ถ้าส่วนต่างไม่ลงตัวเป็นชั่วโมง จะไม่ส่งเวลาจริง (ตั้งเตือนไม่ได้) แทนการเดา
